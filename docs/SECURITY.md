# Security and Trust Boundaries

## Production deployment controls

Production startup rejects missing or development-placeholder database credentials, credential encryption keys, and internal AI tokens. Trusted origins are explicit and restricted to `https://www.arbion.ai`; wildcards and reflected Host/Origin trust are forbidden. Session cookies are `HttpOnly`, `SameSite=Lax`, scoped to `/`, and forced `Secure` in production while localhost development remains usable.

`CREDENTIAL_ENCRYPTION_KEY` is a cryptographically random, base64-encoded 32-byte key generated once per environment. Back it up in a restricted secret store; never commit or casually rotate it. Losing it can make encrypted provider credentials unreadable. Automatic rotation is intentionally out of scope.

Container logs use stdout/stderr, but operators must never log environment dumps or secret-bearing requests. Schwab secrets/codes/tokens, AI API keys, encryption keys, session cookies, internal tokens, and database passwords are prohibited from logs and support bundles. Backups contain sensitive customer and product data and require encryption and restricted access.

## Security posture

Arbion combines probabilistic AI, sensitive financial data, user-supplied credentials, and potentially consequential actions. Its primary invariant is that AI can propose or analyze, but only Arbion-controlled deterministic systems can authorize and dispatch financial operations. This is a target security model, not a statement that integrations or execution are implemented. Authentication is implemented; live and automated trading remain prohibited without a separate explicit task and safety approval.

## Trust zones

### Browser and experience layer

The browser is untrusted. It must not receive stored provider secrets or make authoritative claims about identity, permission, approval, account ownership, risk, or order validity. Client-side checks improve usability but never replace server-side enforcement.

Traditional UI and Ask Arbion are equivalent untrusted inputs to shared structured commands. Natural-language interpretation, conversation history, and actionable notification buttons cannot create a privileged execution path.

### Go control plane

The Go modular monolith is the authentication authority and policy enforcement point. It validates opaque Redis-backed sessions and loads the PostgreSQL user before protected handlers run. Transport handlers and connector adapters cannot bypass domain policy.

## Browser authentication controls

Passwords are accepted only in bounded JSON requests, never logged or serialized, and hashed with encapsulated Argon2id parameters (64 MiB memory, three iterations, two lanes, 16-byte random salt, 32-byte output). Passwords must be 12–1024 bytes; passphrases are encouraged and no composition rule is imposed. Encoded hashes carry their parameters to allow rehash upgrades.

The browser receives a random opaque 256-bit token in an `HttpOnly`, `Path=/`, `SameSite=Lax` cookie. Production also sets `Secure`; localhost development intentionally does not. Only SHA-256 token hashes are Redis keys. Sessions expire after an environment-defined TTL, are rotated at authentication, can be individually deleted, and are indexed for immediate self-service revocation. `GET /api/auth/sessions` is authenticated, `no-store`, capped at 100 active sessions, and exposes only the current session creation/expiry window plus active and other-session counts. It does not collect or return tokens, hashes, IP addresses, user agents, locations, device fingerprints, provider data, or financial data. Malformed, oversized, or unavailable inventory fails closed rather than reporting a clear state.

Cookie-authenticated state changes use an explicit trusted-origin check in addition to `SameSite=Lax`; requests without an allowed `Origin` are rejected. This is the selected CSRF strategy and does not rely on CORS. Login and registration are protected too. JSON decoding rejects unknown fields and trailing values, bodies are capped at 4 KiB, common security headers are applied, and API errors do not expose internals. Redis sliding-window counters currently throttle registration by IP and login by IP plus normalized account identifier without permanent account lockout.

Authenticated users can change their password only after re-entering the current password. The replacement uses the same bounded Argon2id policy, must differ from the existing password, and is rate-limited. Arbion fails closed when the session store is unavailable: it revokes every current session before committing the new password with an optimistic hash check, then clears the current browser cookie. A durable database failure may therefore require the user to sign in again with the unchanged password, but cannot leave old sessions active after a successful password change. The trusted-origin **Sign Out Other Sessions** control atomically removes every indexed browser session except the authenticated current session and records only a safe revoked count in audit metadata. **Sign Out All Sessions** revokes all browser sessions and pending MFA challenges. Neither control deletes financial or AI connections, changes automation state, or requests a broker action.

Audit events record registration, successful and failed login, MFA enrollment/enable/disable and challenge outcomes, logout, other-session logout, all-session logout, and successful or rejected password-change outcomes without passwords, factors, recovery codes, hashes, tokens, network/device metadata, or provider secrets.

Email verification and password recovery use a provider-independent sender boundary. Raw 256-bit tokens exist only in the outbound message and browser URL fragment; PostgreSQL stores a unique SHA-256 hash, purpose, expiry, and consumption time. Creating a new link invalidates the prior active link for that user and purpose. Confirmation is atomic and single-use. Password reset revokes all sessions before committing the new Argon2id password hash. Email request responses are generic for existing, missing, ineligible, and already-verified accounts, and request/confirmation paths are rate-limited. Security messages use a multipart plain-text and escaped HTML body: the HTML alternative carries the existing Arbion wordmark and palette, while the complete plain-text alternative preserves compatibility with restrictive mail clients. SMTP delivery requires STARTTLS with TLS 1.2 or newer and is disabled by default.

Optional authenticator-app MFA uses interoperable RFC 6238 TOTP with a 30-second period, six digits, and one-step clock skew. The Go authentication domain owns enrollment, challenge completion, recovery-code replacement, disablement, order-proposal step-up, Shadow-evidence-review step-up, and audit behavior. A password login for an MFA-enabled account creates only a random five-minute Redis challenge; it creates no authenticated session until the second factor succeeds. PostgreSQL stores the TOTP secret only as AES-256-GCM ciphertext bound to the user and authentication factor through associated data. Ten 80-bit recovery codes are displayed once, stored only as domain-separated SHA-256 hashes, and atomically consumed. An authenticated user can replace the entire recovery set only after re-entering the current password and a valid second factor; all old codes become invalid in the same database statement. Successful TOTP steps advance a durable counter so a code cannot be replayed, including the code used to confirm enrollment. Order-proposal and Shadow-evidence review each accept only a fresh TOTP step—not a recovery code—under separate bounded rate limits and store neither the code nor the secret. Enabling or disabling MFA revokes every existing browser session before the durable change. Setup and disablement require the current password, all state changes require a trusted origin, and failures use generic bounded responses. Arbion does not send MFA codes by email or SMS.

## Required authentication follow-up

The application boundary for verified email and password recovery is implemented, but production delivery must remain disabled until SES production access, a verified sender identity, encrypted SMTP credentials, and an end-to-end owner test are complete. Required verification applies only to newly registered accounts after activation; it does not retroactively lock existing active accounts. MFA is opt-in, but the implemented non-executing Coinbase proposal-review command requires an enabled authenticator factor and a fresh TOTP code. A future live-order policy still requires separate approval and recovery/support review. Passkeys, external OAuth identities, enterprise SSO, cross-user administrative session management, adaptive throttling, and broader step-up authentication remain future security work.

### Python Neural Engine and external AI providers

The Neural Engine is a constrained computational zone. Model output, structured responses, reasoning, tool arguments, and instructions embedded in retrieved content are untrusted. The engine receives only authorized tools and minimized data. It never receives financial-provider credentials and has no direct connector or execution path.

External AI providers are third parties with separate security, privacy, availability, and retention characteristics. Provider selection cannot weaken platform authorization. User-supplied AI credentials are revealed only to the applicable AI adapter/provider flow.

The implemented Arbion Insight flow is intentionally data-isolated. An authenticated entitled user can submit at most 2,000 bytes of text using an active saved OpenAI connection. The request includes no financial account, portfolio, broker, quote, news, or live-market context and exposes no tools. The browser chooses only `fast`, `core`, or `deep`; it cannot supply a model ID. Go and Python bind those profiles to Luna, Terra, and Sol respectively, reject unknown routes, and verify returned route metadata. OpenAI requests set `store: false`, use profile-specific explicit reasoning and output caps, and require a strict JSON schema. A Redis counter enforces a 12-credit hourly budget with weights of one, three, and six; counter failure denies the request. Audit events retain provider/profile/model identifiers, charged credits, byte and token counts, outcome, latency, and provider request ID only; prompt text, model output, credentials, and private chain-of-thought are excluded.

The implemented Coinbase AI proposal flow preserves the credential-class boundary while allowing minimized account facts. The owner fixes the account, asset, side, exact maximum, capital policy, and bounded objective. Go refreshes available USD cash plus only the target asset's total/tradable quantities and sends those normalized values—not a provider account ID, portfolio ID, provider credential, provider preview ID, order ID, or unrelated holding—to the internal Neural Engine. The OpenAI request uses the active encrypted AI connection, Core/Terra route, `store: false`, no tools, a strict proposal/abstention schema, and fixed instructions that treat every supplied field as untrusted data. Python and Go independently enforce the size ceiling and route metadata; Go additionally rejects over-holding SELL output. Only then may Go obtain a fresh Coinbase preview and deterministic risk decision through the existing non-executing path. Abstention obtains no preview. Audit excludes the objective, model thesis, credentials, and account values; submission, execution approval, AI authority, and live execution remain false.

The autonomous AI Shadow Engine extends the same credential separation to Coinbase and Schwab without introducing a broker-write path. One immutable mandate fixes the owner, financial account, AI connection/model, allowlisted symbols, objective, per-decision notional ceiling, capital bucket, session, and SHADOW/FULL_AUTONOMOUS boundary. New AI mandates also require a server-validated daily action ceiling of 1–48; optional minimum-cash, total-exposure, single-position amount, and concentration limits are frozen into the same version and presented back to the owner as a deterministic control envelope. Daily realized-loss limits are rejected for AI SHADOW because authoritative realized profit and loss is not available and must never be inferred. Daily action accounting is scoped to the exact strategy instance and UTC day; abstentions create journal evidence but no execution record and do not consume the action ceiling. Approved OpenAI, Anthropic, and stable Gemini model IDs are bound to their provider and Fast/Core/Deep cost tier in both Go and Python; provider/model mismatches fail before credential retrieval. Each completed journal record freezes that validated AI provider, exact model, and route profile rather than asking an auditor to infer the provider from a model name. Go sends only current normalized cash/buying power, allowlisted positions, provenance-bearing market observations, and at most six validated same-instance decision summaries from the prior six hours. Those summaries contain only decision, symbol, side, deterministic disposition, and timestamp; prior model prose is never fed back. Coinbase trend context is limited to exact 1-hour and 6-hour changes derived from contiguous provider candles; coverage and history provenance travel with the values, gaps are never synthesized, and stale history produces no derived change. Python uses fixed provider destinations, no tools, and strict JSON Schema output, then returns only abstain or one bounded action. OpenAI and Gemini disable provider-side storage per request; Gemini also requests no thinking summaries and explicitly disables tool choice. Go revalidates symbol, side, price, quantity, current SELL availability, response route, mandate version, bucket, breaker, autonomy, risk limits, and a same-instance one-hour identical-action cooldown reconstructed only from immutable SHADOW records. Missing recent-action evidence fails closed. Abstention creates journal evidence only; a permitted proposal reaches only the Shadow adapter, while a held repeat is journaled as risk denied. No preview, order, live reservation, or broker mutation method is invoked.

The SHADOW scorecard's evidence gate is informational and fail-closed. It derives sample counts and time span only from immutable hypothetical outcome marks and derives schedule health only from the owner-scoped durable scheduler row. Missing marks, a short observation window, an unverified schedule, or any consecutive failure remains an explicit blocker. Even `EVIDENCE_REVIEWABLE` grants no role, permission, execution approval, provider call, or live-trading capability.

The authenticated owner may record an acknowledgment only when the gate is exactly `EVIDENCE_REVIEWABLE`, both horizon counts meet the 20-mark floor, the window is at least seven days, the schedule is healthy and last succeeded with zero failures, and the execution boundary remains `SHADOW_ONLY`. The CSRF-protected command requires an explicit non-live statement, the exact current server-computed SHA-256 scorecard fingerprint, and a fresh non-replayable TOTP step. PostgreSQL binds the append-only record to the same owner, AI Shadow instance, mandate, and immutable mandate version and rejects mutation. A later scorecard fingerprint makes the prior review stale without deleting it. The response and audit evidence state `NON_LIVE_EVIDENCE_ONLY`, no broker action, no live promotion, and no execution authority; credentials, MFA codes, holdings, quantities, and provider payloads are excluded.

The owner may also read a bounded reverse-chronological ledger of those immutable acknowledgments. The query keeps both owner and strategy-instance predicates, accepts only a stable opaque `(reviewed_at, id)` cursor and a 1–50 item limit, and is returned with `Cache-Control: no-store`. The projection contains only the stored fingerprint and bounded review-control facts; it exposes no credentials, MFA material, holdings, provider payloads, or private model evidence. If the read projection is unavailable, the interface says so instead of inferring an empty history. Reading the ledger cannot change the AI provider, model, mandate, schedule, order intent, broker state, execution boundary, or live-trading authority.

The per-strategy AI Decision Journal uses the same fail-closed read discipline. Each owner-scoped request accepts only a 1–50 item limit and a stable opaque `(created_at, id)` cursor, returns `Cache-Control: no-store`, and retrieves outcome marks only for execution-record IDs present on that exact page. The browser loads older pages only on owner request and deduplicates immutable identifiers. A failed projection is displayed as unavailable rather than as an empty decision history. Pagination cannot rerun a model, refresh a financial provider, create an order intent, call a broker, mutate history, or grant execution authority.

Per-strategy state and non-live execution history are likewise available only as bounded owner-scoped, `no-store` projections. State history uses a stable reverse `(state_version, id)` cursor; execution history uses `(created_at, id)`; both accept 1–50 items and are loaded 16 at a time by the review UI. The browser projection deliberately omits user and mandate IDs, idempotency keys, action/risk correlation IDs, and arbitrary metadata. It exposes only the immutable state facts and normalized PAPER/SHADOW result facts needed for owner review. Unavailable reads remain unavailable instead of being treated as empty. These routes have no model, provider, broker, mutation, approval, or live-execution dependency.

The downloadable owner Autonomy Evidence Report is a bounded point-in-time projection of the same authenticated automation-review facts. It uses an explicit schema version and source-availability map, retains missing sources as `PARTIAL`, caps all repeated fields, and selects only credential-free control state and aggregate Shadow evidence. It never exports credentials or hints, tokens, raw provider payloads, balances, holdings, quantities, private prompts or rationale, or broker order identifiers. Report generation is local to the rendered review, performs no API mutation or provider/model call, and cannot grant execution authority; the immutable Decision Journal remains authoritative.

### Financial connectors and providers

Financial providers are external systems. Their data and callbacks require authentication, schema validation, provenance, freshness checks, and replay defenses. Go connector adapters receive financial credentials only when needed and only after control-plane authorization. A provider's acceptance of a request does not replace Arbion audit and reconciliation.

Market-source status responses contain only declared source metadata, per-capability process-local attempt/success timestamps, time-bounded current/aged verification state, consecutive-failure counts, bounded categories such as timeout or stale data, configured cache/pacing/verification policy, and capped aggregate counts of valid cache lookups, cache hits, and provider attempts. A provider success expires from current verification after three cache lifetimes within a five-minute-to-one-hour bound. Expiry retains the prior timestamp, creates no failure count/category, and cannot be confused with an observed provider error. The counters have no user, account, instrument, request, or provider-correlation dimension; reset on process restart; and are explicitly not a provider quota or remaining-credit balance. They never expose raw provider errors, response bodies, request URLs, headers, correlation values not already approved as observation provenance, or credentials. Invalid caller input never enters request telemetry, a cache hit does not create a provider-success event or extend verification, and status metadata is never presented as an executable quote, observation-freshness guarantee, or provider event timestamp.

Durable market-source health is stored independently as five-minute aggregate buckets with a hard 30-day write-time retention boundary. The schema permits only the production source/capability allowlist, `VERIFIED` or `DEGRADED` completed outcomes, and the same bounded failure categories used by runtime status. It has no foreign key or column for users, accounts, instruments, symbols, requests, credentials, provider request IDs, URLs, payloads, or raw errors. The authenticated browser contract exposes only a fixed 24-hour hourly view and rejects added subject fields or semantic expansion. A persistence failure is ignored by the source read after a short database deadline; the history route fails closed and never leaks the storage error.

The market watchlist is a durable Arbion preference, not provider authority. Every row is owner-scoped, limited to canonical crypto symbols and fixed USD venue observation, unique per owner, and cascade-deleted with that owner. Creation takes an owner-specific transaction lock before enforcing the hard 12-row ceiling, so concurrent requests cannot exceed the bound. Add and delete endpoints require authentication and an approved request origin; deletion always includes the owner in its predicate. These mutations never receive Coinbase credentials or call a Coinbase write method. Watchlist reads use only the keyless public adapter and preserve the saved row during provider failure, while omitting raw diagnostics and declaring provider writes, order actions, and execution unavailable.

### Data infrastructure

PostgreSQL is the durable system of record. Redis is ephemeral and must not be the sole store for authorization, approvals, credential state, or audit facts. Production infrastructure requires encrypted transport, encryption at rest, backups, least-privilege identities, network restrictions, and monitored access.

Login sessions are short-lived browser authorization state, not ownership of stored resources. Logout must not delete persistent provider connections or disable authorized, server-side automation. Automation enablement and configuration remain authoritative in PostgreSQL and survive browser closure, logout, process restarts, and Redis loss.

## Credential classes

AI-provider and financial-provider credentials must be stored, authorized, audited, rotated, and revoked as distinct secret classes. Access to one class never implies access to the other.

| Secret class                       | Permitted consumers                                                 | Must not reach                                                                                          |
| ---------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| AI-provider credentials            | Secret-management boundary and selected AI adapter/provider request | Financial providers, unrelated adapters, logs, analytics, or browser responses after storage            |
| Financial-provider credentials     | Secret-management boundary and selected Go connector adapter        | Neural Engine, AI providers, prompts, tool results, logs, analytics, or browser responses after storage |
| Platform keys and session material | Narrow platform infrastructure components                           | AI/financial providers, application payloads, logs, or client-visible configuration                     |

Secrets must never be committed to Git. Configuration examples use safe development values or blank placeholders. Production storage must use managed secret storage or strong application-level encryption with separated key management. Logs, traces, metrics, support tooling, exception reporting, and backups need consistent redaction and access controls.

The development credential vault encrypts each payload with AES-256-GCM and binds ciphertext authentication to its user, connection, and AI-versus-financial credential class. Only encrypted payloads are persisted in PostgreSQL; normal provider models contain safe metadata only. The vault interface allows a future managed KMS or secrets-manager adapter. Production key custody, rotation, and managed-secret selection remain deferred.

AI connection endpoints authenticate every request, scope every lookup and mutation by user ID and the `ai` credential class, enforce trusted origins on mutations, and cap JSON bodies and API keys. Foreign and missing connection identifiers are indistinguishable. Audit events contain provider/connection identifiers and state transitions but no request body, key, ciphertext, nonce, or vault details. Logout removes only the session and has no connection lifecycle side effect.

Disruptive AI connection changes fail closed before credential or status mutation. Removal checks Neural preferences, current mandates, and immutable mandate-version provenance. Disablement additionally checks READY/PAUSED mandates and ACTIVE/PAUSED runtimes using each instance's pinned immutable version, preventing a newer DRAFT from hiding an older runtime dependency. Active key rotation first stores only an AES-GCM-encrypted candidate in a column runtime reads never select, verifies the supplied candidate through the fixed registered adapter, and then promotes it with one owner/category/status/generation/token-bound database update. The 256-bit random staging token prevents overlapping requests from activating a different candidate, while the monotonic generation prevents stale verification from changing newer state. Failure or interruption preserves the current verified key; cleanup can discard only the matching candidate, and any residual encrypted stage remains runtime-ineligible until a later stage overwrites it or the connection is removed. Plaintext, staging tokens, and candidate ciphertext never enter browser responses, logs, or audit metadata.

For verification, model discovery, bounded insight, and bounded trade research, Go checks entitlement, ownership, and state before retrieving plaintext through the Vault. It sends the AI credential in a bounded JSON body over an internal-only, bearer-authenticated service route; it never uses an environment variable or query string. Python holds it only for request scope, selects a fixed adapter destination, bounds time and response size, performs no uncontrolled retry, and returns only normalized results or errors. Financial credentials are never part of that body. Raw provider bodies are never relayed. Local Compose does not publish the AI port; production additionally requires encrypted transport, workload identity/rotation, restrictive network policy, and trace/log redaction.

**AI provider verification does not grant trading authority. AI provider credentials never cross into financial-provider connectors.**

## Financial action boundary

AI output enters the control plane as an untrusted proposal. Before any future financial action, the platform must establish:

1. authenticated actor and tenant context;
2. account ownership and current connection state;
3. permission and explicit intent for the requested operation;
4. account status, buying power, positions, and current relevant data;
5. deterministic risk and order validation;
6. required human or policy approval;
7. execution policy, idempotency key, and failure behavior; and
8. tamper-evident audit and post-operation reconciliation.

No prompt, model selection, confidence score, tool call, or provider response can waive these checks. Direct live execution and automated trading require explicit future design approval and are not part of the current system.

The active immutable Automation Mandate version is an additional authorization ceiling for automation. Available broker buying power is not consent to deploy capital; explicit capital buckets, reservations, protected amounts, and absolute limits constrain use. Autonomy changes human-approval requirements but never weakens the deterministic gate.

Hard circuit breakers cover loss/deployment limits, reserves, concentration/frequency, connectivity, stale or abnormal data, volatility, execution failures, reconciliation mismatch, capability changes, and scoped kill switches. They fail closed for affected new action and cannot be overridden or reset by AI. The implemented owner-facing automation, financial-account, and owner-wide emergency stops require a reason and explicit confirmation, preserve durable timestamps and actor identity, and produce audit evidence without requesting a broker action. An account stop affects only new actions tied to that owner/account; the owner-wide stop affects only the authenticated owner's resources. A platform-wide stop additionally requires a current active superadmin, can be engaged without delay, and requires a freshly consumed TOTP step to release. It applies to every risk-gated action but cannot close positions or contact a broker. See [Risk and Control Engine](RISK_CONTROL_ENGINE.md).

The production operations snapshot is a separate read-only superadmin surface. Middleware checks the authenticated role and its service rechecks active superadmin status in PostgreSQL before running one aggregate query. Its schema deliberately excludes user, account, instrument, symbol, provider identifier, credential, request, and raw-error fields. It reports only control-plane counts and fixed summaries, marks live execution and broker action false, uses `no-store`, and cannot change a breaker or call a provider.

Future submission must be idempotent and duplicate-resistant. Submission or provider acknowledgement is not a fill. Broker truth is authoritative for execution state, and reconciliation must detect partial fills, cancellations, rejections, external trades, drift, and lost acknowledgements before dependent strategy state advances. See [Execution Engine](EXECUTION_ENGINE.md).

## Tool boundary

Internal MCP-like tools are deny-by-default capabilities, not raw network or database access. Each invocation must bind to an identity, tenant, account, purpose, schema version, permission set, deadline, and audit correlation identifier. Inputs and outputs are validated and minimized. Tool descriptions and retrieved content are data, not policy instructions.

A future MCP-compatible server for external clients would introduce a new public trust boundary and requires separate threat modeling and approval. It must reuse, not bypass, the control plane.

## Audit and observability

Administrative endpoints enforce centralized, deny-by-default role checks. Product entitlement is never interpreted as an administrative role, and administrative role is never interpreted as product access. Founder protections are domain invariants in the mutation service and database constraints, not client-side controls. Rejected privileged changes return a generic forbidden response without exposing sensitive account state.

Security-relevant events should capture actor, tenant, decision, policy version, resource, time, correlation identifiers, approvals, and outcome. Audit records must avoid secrets and unnecessary sensitive payloads, be access-controlled, have defined retention, and eventually support integrity protection. Operational telemetry should default to metadata rather than prompts, model responses, order payloads, or provider bodies.

Automated and AI-assisted actions also require a structured Decision Journal linking the exact mandate version, strategy state, market references, concise rationale, risk checks, approval, order, broker response, and resulting state. Arbion does not store private model chain-of-thought. Explainability uses these records rather than model guesswork.

## Threats to address before integrations

- prompt injection and tool-confusion attacks;
- cross-tenant or cross-account access;
- excessive OAuth scopes and token theft;
- secret leakage through logs, traces, errors, URLs, support exports, or model context;
- forged or replayed OAuth callbacks and webhooks;
- stale, manipulated, or incorrectly normalized financial data;
- duplicate, reordered, ambiguous, or partially completed side effects;
- provider compromise, outage, rate limiting, and dependency substitution; and
- unauthorized automation or approval bypass;
- capital double allocation or stale mandate/version use;
- circuit-breaker bypass or unaudited emergency reset; and
- execution-state confusion caused by treating submission as a fill.

## Required future security decisions

Before product integration work, Arbion must choose its identity and tenancy model, authorization policy system, consent and step-up approval design, secret manager and cryptographic ownership, data classification and retention policy, external audit archival and cryptographic anchoring, AI-provider privacy requirements, connector OAuth scopes, incident-response process, and formal threat models for tools, connectors, MCP, and any execution workflow.

Platform audit rows are append-only at the PostgreSQL boundary: updates and deletes are rejected for every event, including existing history. The authenticated `GET /api/auth/security-activity` route is owner-scoped, bounded to 1–100 rows, `no-store`, and stably paginated by opaque time/ID cursor. It selects only an explicit set of access, provider-connection, autonomy-policy, non-executing approval, authorization, and emergency-control actions and returns only immutable ID, controlled action code, and occurrence time. The website maps those codes to fixed Arbion copy. Audit metadata, actor/target identifiers, email and network attributes, provider responses, credentials, portfolio data, and broker data remain outside the projection. This is append-only database enforcement, not a claim of external cryptographic anchoring or indefinite archival retention.

The owner Attention Center is a separate current-state projection, not a replacement for immutable audit or decision history. `GET /api/owner/attention` requires the established authenticated session, applies the owner predicate in every scoped branch, is capped at 50 rows and marked `no-store`, and uses a fixed allowlist of condition codes and severities. Global stops are intentionally visible to every owner; user, account, and automation stops are included only when the resource belongs to the authenticated owner. Account/provider names, credential material and metadata, provider payloads and raw errors, holdings, symbols, quantities, reconciliation changes, breaker reasons, order data, and approval or execution controls are absent. Database/query failure returns a generic service-unavailable response, and the dashboard explicitly refuses to infer a clear state.

## Financial authorization implementation controls

Schwab app credentials are infrastructure secrets; user OAuth grants and Coinbase key pairs are per-user financial Vault records authenticated to user, connection, and secret class. Tokens, key names, private keys, and portfolio identifiers are never connection metadata, database plaintext columns, audit metadata, URLs, browser storage/responses, or Neural Engine input. Only the selected Go adapter receives decrypted financial credentials for a bounded request. Conversely, AI Vault records are retrieved only by the AI connection domain and can never be selected by a financial locator. Tests cover this AAD-enforced class separation and safe JSON projections.

Pending OAuth state is random, expiring, user-bound, and single-use. A mismatched attempt consumes the state to stop swapping attempts. Provider redirects are fixed configuration, not request parameters. Read bodies and durations are bounded; authentication failures are not retried. Concurrent token refresh must be serialized by connection, encrypted replacement must complete before expiry metadata/status changes, and terminal authorization failure fails closed without leaking the provider body.

Coinbase API-key enrollment is authenticated and CSRF-protected. The authenticated client rejects a plain one-line secret before transmission because Coinbase App requires an ECDSA key; optional downloaded key JSON is parsed locally. Go canonicalizes Coinbase's quoted, literal-PEM, and escaped-`\n` representations, validates the ECDSA P-256 key, generates a request-specific ES256 JWT, and calls Coinbase's permission endpoint before writing any connection material. Enrollment fails closed unless View is present and Transfer is absent. Trade may be present, but is recorded only inside the encrypted financial credential and projected as a provider capability; it is not Arbion approval or execution authority. The key is never interpolated into a URL or provider error, and provider response bodies are bounded and discarded on failure. Safe failure codes distinguish local format errors, Coinbase authentication rejection, and unsafe permissions; audits include no credential values.

The Coinbase portfolio command endpoint is an authenticated, owner-scoped `GET` with `Cache-Control: no-store`. It reuses the financial read boundary, which re-verifies View and the absence of Transfer before current balance and holding reads. The adapter bounds and paginates both Coinbase App wallet/vault inventory and Advanced Trade Portfolio Breakdown, reconciles same-currency totals without summing overlapping provider views, and uses Advanced Trade only for explicitly reported tradable quantity. Quantity outside that report is conservatively unavailable to trade, so it cannot increase sell authority. Only normalized symbols and exact quantities reach the separate public market adapter. Venue pricing is bounded to 32 assets per refresh and uses exact decimal arithmetic. USDC in a USD-base account is valued through a fixed, separately labeled Coinbase 1:1 redemption reference; it is excluded from venue requests and receives no fabricated quote or timestamp. Missing products and provider failures remain explicit coverage gaps, and no equivalent peg is inferred for other stablecoins. No credential, wallet UUID, portfolio UUID, raw provider body, order-submission method, or transfer method enters the response.

The unified holdings ledger preserves the same owner-scoped boundaries while loading connected accounts independently. A failed account read creates a named coverage warning; it cannot clear another account, synthesize a zero position, change connection state, or mutate an automation. Schwab average price and current-day/open profit-and-loss are normalized only from bounded provider position fields. Current unit price and open-return percentage use exact decimal arithmetic with an explicit instrument multiplier and remain labeled as position-derived display facts. Coinbase rolling 24-hour movement uses only the keyless public ticker/statistics adapters. Coinbase spot cost basis and total return remain absent because bounded fill history is not an authoritative tax-lot ledger. No cross-provider row, summary, filter, or search operation contacts a provider write API or changes the risk/execution boundary.

The owner-triggered portfolio reconciliation routes are authenticated, owner-scoped, `no-store`, and CSRF-protected for snapshot creation. The non-live scheduler may invoke the same reconciliation service only for an active `AI_AUTONOMOUS` instance immediately before its SHADOW evaluation, using the owner and financial-account identity recovered from the already-authorized durable schedule claim. One run retrieves only the selected account's current normalized balance and position feeds through the existing financial credential boundary, caps positions at 1,000, rejects malformed or duplicate normalized positions, and atomically appends an evidence-hashed snapshot plus position rows. Manual and scheduled runs share a per-owner/account PostgreSQL advisory lock. PostgreSQL rejects updates and deletes. The separate history route is a bounded cursor-paginated `GET` over stored summaries and exact change evidence only; every cursor is resolved inside the same owner/account boundary, responses omit position inventory, and browsing history performs no provider or Vault read. Missing evidence creates one enforced `BASELINE`; automatic confirmation waits at least 30 minutes. A healthy `MATCHED` snapshot refreshes only after 12 hours, before the 24-hour risk expiry. `INCOMPLETE` evidence retries no more often than hourly, while `DRIFT_DETECTED`, malformed, future-dated, or unknown evidence is never automatically cleared. When the latest snapshot is `DRIFT_DETECTED`, the manual route also fails closed unless the authenticated owner submits both an explicit review acknowledgement and the exact current immutable reconciliation ID. An omitted acknowledgement returns `RECONCILIATION_REVIEW_REQUIRED`; a stale identity returns `RECONCILIATION_CHANGED` before any provider read. A successful owner-reviewed snapshot records `OWNER_DRIFT_REVIEW`, `reviewed_prior_drift=true`, and that exact reviewed reconciliation ID in credential-free audit metadata. A complete first observation is `BASELINE`; later complete observations compare exact rational quantities by symbol, instrument, and direction and emit only appeared, disappeared, or quantity-changed evidence. For Coinbase only, a quantity change is classified as non-blocking when the position exists in both snapshots, available-to-trade is exactly unchanged, unavailable-to-trade changed, and each provider snapshot exactly satisfies total = available + unavailable. Arbion records the full change but does not infer whether staking, rewards, restrictions, or another provider condition caused it. Missing components, arithmetic disagreement, appeared/disappeared positions, and any available-to-trade movement remain blocking drift. Provider feed failure is preserved as `INCOMPLETE` and never converted into zero holdings. Supported Schwab position performance is stored only when average price, current price, and open profit/loss are all provider supplied. Coinbase cost basis and all realized profit/loss remain explicitly unavailable and are never reconstructed from its bounded fill window. New enforced snapshots fail closed for autonomous AI proposals: `BASELINE`, `INCOMPLETE`, blocking `DRIFT_DETECTED`, and evidence older than 24 hours hold only the new proposal, while a complete `MATCHED` snapshot clears the gate even when it retains exact non-tradable-only change evidence. Historical advisory snapshots retain their original semantics and cannot clear the gate. Scheduled reconciliation failure stores only `RECONCILIATION_REFRESH_FAILED` and prevents the model evaluation for that cycle. This control cannot pause an instance, alter a holding, acknowledge drift automatically, or call a preview, submission, transfer, cancellation, or other broker-write operation.

Automation mutations require centralized `CanUseAutomation` and financial-account entitlement checks; AI-bearing mandates additionally require `CanUseNeuralEngine`. Administrative roles do not grant these product capabilities. Stores scope account, bucket, mandate, version, and AI references to the user; active AI/model preference checks occur without invoking AI or revealing credentials. Version snapshots and audit metadata contain identifiers and safe configuration only.

The API exposes configuration and lifecycle routes plus one authenticated, CSRF-protected manual PAPER/SHADOW strategy-evaluation route. That route accepts only an instance ID and bounded idempotency event ID. Both paths use fresh read-only inputs and pass every proposal through the Risk/Control Engine. Scheduler completion atomically advances the current schedule pointer and inserts an immutable owner/instance/mandate-bound run record; raw errors, credentials, provider payloads, symbols, and broker instructions cannot enter that schema. Its authenticated `GET /api/strategy-instances/{id}/schedule-runs` projection is `no-store`, bounded, stably paginated, and exposes only safe timing, control status, reconciliation identity, and non-live disposition. No role, model, strategy, UI, or conversation may bypass the Risk/Control Engine. ## Non-live strategy security boundary

Strategy state, transitions, market fixtures, paper records, schedule status, and Decision Journal rationale contain only normalized safe data. They exclude financial/AI credentials, full account numbers, raw provider payloads, raw provider errors, and private chain-of-thought. Ownership and `CanUseAutomation`/financial entitlement are checked server-side for instance APIs; scheduled claims independently require a current active founder entitlement.

Every strategy instance stores the capital bucket copied from its exact immutable mandate version and enforces that binding with a same-owner database foreign key. Initialization atomically creates a durable, exact non-live capital reservation. A partial unique index rejects direct active bucket reuse. PostgreSQL serializes claims per owner/account and permits multiple active or paused instances only when every exact same-currency amount shares the same explicit fixed-allocation account ceiling and the aggregate fits; incompatible or unresolved policies retain an exclusive account claim. PAPER starting cash is parsed as an exact bounded decimal and cannot exceed the fixed allocation or absolute percentage cap after protected capital. SHADOW requires fixed protected capacity or an explicit percentage-bucket absolute cap. Paused instances retain their claim, policy fields are frozen while claimed, and completion releases it atomically without deleting evidence. These reservations do not lock broker funds or grant execution authority.

The authenticated `GET /api/strategy-capital-reservations` inventory is an owner-scoped, `no-store` read projection over active non-live claims; released evidence remains available through the individual strategy review instead of expanding the account-wide current-state response. It requires the automation entitlement and explicitly reports that broker funds are not locked, broker action is unavailable, live execution is unavailable, and no execution authority is granted. The Capital Center fails closed if any connected-account, bucket, reservation, or strategy inventory is unavailable, performs exact-decimal same-currency aggregation only, and links each active claim back to its owning strategy without creating a model, provider, broker, approval, or execution path.

An authenticated, CSRF-protected owner command may pause an active PAPER/SHADOW instance under expected-version concurrency. Pause advances the version and appends immutable same-state `PAUSED` evidence while retaining the account claim; manual and scheduled evaluations require `ACTIVE` and therefore stop. Resume requires a second explicit non-live acknowledgement and atomically verifies that the instance's exact immutable mandate version is still both current and `READY` before recording `RESUMED`. A paused PAPER Wheel may resolve an already-open simulated lifecycle event without resuming, and the instance remains paused afterward. These commands have no execution adapter or provider call.

Releasing the conservative account claim requires an authenticated, CSRF-protected owner command with the expected state version and an explicit non-live confirmation. The database locks and terminally completes only an active or paused owner-scoped instance, and PAPER release is rejected while any simulated option or share quantity remains nonzero. A successful finish advances the optimistic version and appends immutable transition evidence; the service separately records a safe audit event. It cannot delete history, modify the PAPER ledger, contact a provider, or send a broker order.

The aggregate `GET /api/decision-journal` route applies the same product entitlements and filters every joined record by the authenticated user. It exposes a bounded, no-store, read-only projection with opaque stable pagination. The owner-scoped `GET /api/strategy-instances/{id}/paper-portfolio` route independently constrains the simulated portfolio, strategy instance, and positions to that same owner, returns normalized ledger facts only, and rejects SHADOW instances. The website labels PAPER as simulation and SHADOW as would-have-submitted evidence, and the API continues to declare `live_execution_available=false`.

Guarded schedule email is an opt-in field of the immutable mandate version and is available only when SMTP delivery is configured. The claim query obtains only the owning user’s normalized verified address and the applicable boolean notification choices. Messages are created after durable schedule completion, use Arbion’s branded multipart template, contain only mode, scheduled time, a safe result code when applicable, an owner review link, and the bounded AI Shadow evidence-gate label described below, and explicitly state that no broker order was sent. For an AI Shadow version already opted into completed-evaluation email, the scheduler may read the owner-scoped PostgreSQL scorecard after durable completion and label that same message `COLLECTING_EVIDENCE` or `EVIDENCE_REVIEWABLE`; an unavailable or unrecognized gate falls back to the generic completion message and can never invent readiness. This enrichment adds no email, provider/model call, approval, or execution authority. Lifecycle-required and first-failure messages are edge-triggered. An AI Shadow mandate may separately opt into a credential-free account review email when a successful cycle observes a new immutable `DRIFT_DETECTED` reconciliation with blocking tradable-inventory changes. The email contains no symbol, quantity, provider payload, approval, or acknowledgement control. Only after delivery succeeds does the schedule store that exact immutable reconciliation ID; PostgreSQL verifies the evidence is blocking and belongs to the same owner and financial account. The same ID is suppressed on later cycles, a new evidence ID creates a new edge, and a delivery failure leaves the marker unchanged for a later retry. A crash between external SMTP acceptance and the marker write can produce a duplicate email, so the contract is durable evidence-ID deduplication rather than exactly-once delivery. Delivery errors do not expose recipient addresses or provider text in logs and cannot alter, approve, acknowledge, or execute a strategy result.

The guarded scheduler uses an explicitly reviewed NYSE calendar for published 2026-2028 holidays and early closes. Its normal window remains 9:35 a.m.–3:55 p.m. America/New_York; early-close days end at 12:55 p.m., five minutes before the published 1:00 p.m. equities close. Weekends, listed closures, and times outside the window make no provider call. An expired calendar horizon becomes a stable failure and retries no more often than daily; it is never interpreted as an open market. Unexpected exchange closures still depend on the existing fresh-data checks to fail closed.

PAPER and SHADOW traverse the same Risk/Control Engine. PAPER mutates only separate simulated tables; SHADOW mutates no holdings and explicitly records that no order was sent. The strategy package imports neither Schwab nor Neural Engine code; a credential-aware financial service supplies only normalized read models. Missing, stale, or future-dated market timestamps fail closed. No live or broker execution adapter exists.

## AWS production trust boundaries

The AWS foundation exposes only the ALB. ECS tasks have no public IP; AI accepts only API-security-group ingress; RDS and ElastiCache are private and accept only explicitly authorized task groups. NAT provides outbound HTTPS without adding inbound reachability. Cloud Map network discovery does not replace the AI internal token. Financial-provider secrets remain consumable only by Go, and Neural Engine tasks receive no Schwab or database credentials.

GitHub authenticates with repository- and production-environment-restricted OIDC roles, never static AWS access keys. Separate Terraform plan/apply and application deployment roles are distinct from least-privilege ECS execution/task roles. Secrets Manager contains operator-populated values encrypted under KMS; Terraform creates containers and never stores values in source or outputs. RDS credentials are AWS-managed, Redis requires TLS and authentication, and the stable application credential-encryption key is not interchangeable with a KMS key.

Deletion protection, final snapshots, secret recovery windows, protected state/KMS resources, manual apply/deploy approval, and DNS-disabled-by-default settings reduce accidental production loss or takeover. No AWS resource was created as part of repository preparation, and live broker execution remains absent.
